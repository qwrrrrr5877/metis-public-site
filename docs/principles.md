# Metis Principles

Metis is built around one premise: judgment systems only improve when their
claims, evidence, errors, and lessons are made into durable objects.

The system is not trying to make every forecast public, automatic, or
high-confidence. It is trying to make reasoning inspectable enough that future
reasoning can learn from it.

## 1. Forecasts Are Objects, Not Vibes

A forecast should have a defined question, timing, resolution rule, evidence
state, and owner. Without that shape, it is too easy to remember the feeling of
a call while forgetting what was actually claimed.

Metis separates:

- hunches,
- watch objects,
- candidate predictions,
- registered predictions,
- lessons,
- and promoted patterns.

That separation keeps exploratory thinking alive without polluting calibration.

## 2. Watch Objects Can Teach Without Becoming Calibration Samples

Not every useful judgment deserves to become a formal prediction. Sometimes the
right move is to watch an event, record the reasoning, and learn from the
outcome without pretending the evidence quality was high enough for a registered
forecast.

This matters because a system can learn from weak signals while still protecting
its calibration record.

## 3. Engines Own Local Context; Core Owns Shared Discipline

Each engine is allowed to be domain-specific. A central-bank engine, a
semiconductor-capex engine, and a regulatory-committee engine should not be
forced into the same internal language.

Metis Core stays small on purpose. It asks each engine to expose enough shared
surface to coordinate:

- what changed,
- what evidence moved,
- what needs human review,
- which lessons may transfer,
- and whether core rules still fit.

The core does not replace local judgment. It keeps local judgment from becoming
unreviewable.

## 4. A Correct Narrow Prediction Can Still Miss The Structure

Being right on a narrow object is not the same as understanding the event.

The FOMC engine's recent work is a good example: a meeting can satisfy a narrow
dissent-count view while still revealing a richer vote topology. Metis treats
that as a useful success and a useful warning at the same time.

The system should ask:

- What did we get right?
- What did the prediction fail to represent?
- Did the event expose a missing object type?
- Should this become a lesson, a pattern, or only a note?

## 5. Lessons Must Survive Compression Before Becoming Rules

Metis does not promote every postmortem insight into a reusable rule.

A lesson should survive:

- source review,
- counterexample search,
- comparison with prior cases,
- domain boundary checks,
- and compression into a smaller transferable form.

Rules are expensive. Bad rules travel faster than good hunches.

## 6. Public Notes Explain The Method; Private Ledgers Remain The Memory

The public site exists to explain the framework, selected patterns, and
sanitized progress. It is not the full system of record.

Private engine ledgers keep raw evidence, unresolved prediction internals,
schema details, source files, and human review notes. That boundary is part of
the design, not a temporary omission.

## 7. Human Review Is A Feature, Not A Bottleneck

Metis should automate repetition, not judgment surrender.

The system can surface stale objects, prepare packets, collect evidence, and
check rule compatibility. But schema changes, lesson promotion, public release,
and high-consequence interpretation should remain legible to a human reviewer.

The point is not to remove the human. The point is to make human attention land
where it has the most leverage.
